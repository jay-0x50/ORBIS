# M1.5 재화 · 동료 모집 구현과 테스트

M1.6 이후 현재 저장 버전은 **3**이며, 주인공 선택·원소를 추가했습니다. 기존 재화·피티·월드 진행은 보존됩니다. 새 게임 시작은 [M1.6 선택 화면](M16_구현_테스트.md)을 사용하세요.

06번 기획서의 재화 데이터, 캐릭터 모집 로직, 동료 18명의 로스터 데이터를 전용 데모에서 확인합니다. 기존 M0~M4의 이동·전투·탐사·지역 씬과 애셋 표현은 유지합니다. 모집으로 얻은 동료 데이터는 이번 단계에서 실제 파티 편성이나 신규 스킬·모델 해금에 연결하지 않습니다. 실제 결제, 무기 배너, 세 번째 특수 배너, 배너 기간 자동 전환도 추가하지 않습니다.

## 씬 실행

1. 프로젝트를 설정된 Unity 6 에디터로 엽니다.
2. 메뉴 `Orbis > M1.5 > Setup and Validate`를 실행합니다. 캐릭터·확률·배너·카탈로그 ScriptableObject와 데모 씬을 생성하고 연결을 검증합니다. 기존 Build Settings는 보존하고 데모 씬만 뒤에 추가합니다.
3. 메뉴 `Orbis > M1.5 > Open Gacha Demo`로 `Assets/Orbis/M15/Scenes/M15_GachaDemo.unity`를 엽니다.
4. Play를 누릅니다. 마우스로 한정/상시 탭과 버튼을 조작합니다. 작은 Game 뷰에서는 화면 전체를 스크롤할 수 있습니다.

신규 저장은 재화 6종과 보유 동료가 모두 0입니다. 기존 M4 저장을 사용하는 경우 기존 코인은 같은 수량의 루멘으로 이전되어 처음부터 표시될 수 있습니다. 개발용 지급 버튼은 Editor 또는 Development Build에서만 나타나며, 실제 로컬 저장에 지급 결과를 남깁니다.

## 수동 점검 순서

1. **재화 부족**: 서약서가 없는 새 저장에서 `1회 모집`과 `10회 모집`을 누릅니다. 부족 안내가 나타나고 재화·보유 현황·천장 카운터는 변하지 않아야 합니다. 기존 저장에 서약서가 있다면 자동 테스트의 임시 저장 케이스로 이 조건을 확인합니다.
2. **교환**: `결정 +1600`을 누르고 한정 탭에서 `서약서 10장 교환`을 누릅니다. 오르빗 결정이 1600 감소하고 인연의 서약서가 10 증가합니다. 상시 탭에서는 동일 비용으로 표준 서약서만 늘어납니다. 현재 비용은 버튼에 실제 Rules 값으로 표시됩니다.
3. **모집 결과**: 해당 탭에서 `10회 모집`을 실행합니다. 해당 종류의 서약서가 정확히 10 감소하고 최근 결과 10개, 신규 `NEW` 표시, 누적 보유 장수가 나타납니다. 중복 획득은 보유 장수만 증가하며 다른 재화로 변환하지 않습니다. 10회는 차감·결과·보유·천장을 한 번의 저장으로 반영합니다.
4. **배너 독립성**: 한정과 상시 탭을 번갈아 열어 `5성 미당첨`과 `4성 이상 미당첨`을 비교합니다. 한 배너에서 모집해도 다른 배너 카운터는 증가하지 않습니다. 한정 픽업 보장은 한정 배너에만 표시됩니다.
5. **표시 스킵**: `연출 스킵`을 켜고 모집합니다. 결과 목록과 저장은 동일하게 처리되며 `표시 요청 이벤트` 횟수만 증가하지 않습니다. 체크를 해제하면 성공한 결과마다 이벤트 횟수가 증가합니다. 이 데모는 간단한 텍스트 이벤트 표시만 사용하며 06/08번의 카드 애니메이션·5성 7단계 연출·신규 VFX는 구현하지 않습니다.
6. **스타터 지급**: `튜토리얼 완료 모의: 스타터 3명 지급`을 누릅니다. 카이런·밀라·토르반을 각각 1장 지급합니다. 이미 모집한 스타터도 무료 지급 1장은 추가됩니다. 같은 저장에서 버튼을 다시 누르면 이미 지급한 안내가 나오고 보유량이 더 늘지 않습니다. 실제 튜토리얼 퀘스트는 이 버튼에 연결하지 않습니다.
7. **저장 유지**: 잔액·보유량·두 배너 천장을 확인하고 `저장`, `저장 다시 읽기`를 차례로 누릅니다. 같은 값이 유지되어야 합니다. Play를 종료하고 다시 시작해도 값과 스타터 지급 완료 상태가 유지됩니다. 최근 결과 카드 목록은 이번 데모 실행 중의 표시 기록이며 보유 현황과 구분됩니다.
8. **기존 보상 연결**: M4 지역 씬에서 위임/보스 보상을 수령한 뒤 데모를 다시 엽니다. 기존 코인 잔액과 데모 루멘은 동일한 저장 필드를 읽습니다. 다른 재화는 기존 M4 보상에서 임의로 추가 지급하지 않습니다.

## 데이터와 확률

카탈로그는 `Assets/Orbis/M15/Resources/M15/Catalog.asset`입니다. `Characters/`에는 18개의 캐릭터 SO, `Banners/`에는 한정·상시 배너 SO, 같은 폴더에 `Rules.asset`이 있습니다. `Resources.Load<GachaCatalog>("M15/Catalog")`로 읽습니다.

| 설정 | 최초 기본값 | 의미 |
| --- | ---: | --- |
| 3성 / 4성 / 5성 | 94.3% / 5.1% / 0.6% | 기획서의 약 94%를 합계 100%가 되도록 94.3%로 보완 |
| 소프트 천장 시작 | 74번째 | 5성이 나오지 않은 연속 모집의 다음 회차 기준 |
| 소프트 천장 증가 | 회당 6%p | 기획 미정 기본값. 74번째 5성 확률은 6.6%, 75번째는 12.6% |
| 하드 천장 | 90번째 | 해당 회차는 5성 100% |
| 소천장 | 10회 | 4성 이상이 없으면 10번째는 4성 또는 5성. 5성 획득도 이 카운터를 초기화 |
| 한정 픽업 | 50% | 5성 판정 후 픽업 판정. 실패하면 다음 한정 5성은 픽업 확정 |
| 서약서 1장 비용 | 결정 160개 | `CurrencyManager.Exchange`가 사용하는 공용 Rules 값 |

소프트 천장 증가분은 3성 확률에서 먼저 차감하며 가능한 한 기본 4성 확률을 유지합니다. 소천장과 5성 천장이 겹치면 5성이 우선합니다. UI의 기본 확률은 SO를 읽고, `다음 1회` 확률은 실제 `GachaEngine.NextOdds` 결과를 표시합니다. 같은 등급 풀 내 선택은 균등하며 한정 5성은 픽업 판정 후 나머지 풀을 선택합니다.

`Setup and Validate` 재실행 시 기존 SO의 GUID를 유지합니다. 기존 `Rules.asset`의 수치는 덮어쓰지 않으므로 Inspector에서 조정한 확률·비용을 보존합니다. 확률 합계·유한 값·양수 임계값 등 데이터 검증은 통과해야 합니다. 캐릭터 기준 데이터와 배너·카탈로그 참조는 설정 명령이 다시 연결하므로 해당 구조를 변경하려면 빌더의 기준 정의도 함께 관리합니다.

한정 배너는 `별을 가르는 물결`, ID `limited.maris.001`, 픽업 마리스입니다. 상시는 `여정의 동행`, ID `standard.companions`입니다. 사용자가 확정한 범위에 따라 기존 5성 5명이 상시 풀에도 들어가며, 한정 픽업 실패 풀에서는 현재 픽업을 제외한 나머지 4명을 선택합니다. 스타터 3명은 무료 지급 대상이면서 3성 모집 풀에도 포함됩니다. 배너의 이름 변경은 천장 저장 ID를 바꾸지 않습니다. 신규 시즌을 추가할 때에는 신규 ID와 보장 이전 정책을 명시적으로 정해야 하며 이 데모는 달력으로 자동 회전하지 않습니다.

## 저장과 호출 계약

기존 `M4Session.Progress`가 사용하는 `Application.persistentDataPath/Orbis/m4-progress.json`에 재화·보유·천장을 함께 저장합니다. 데모 하단에 실제 전체 경로를 표시합니다. 저장 형식은 버전 2로 확장하고 기존 버전 1의 `coins`를 루멘으로 이전합니다. 기존 일일/주간 위임·보스 기록은 보존합니다. 정상 백업을 활용하는 기존 복구 흐름과 손상/미래 버전의 읽기 전용 보호도 유지합니다.

`CurrencyManager`는 `Add`, `Spend`, `Exchange`, `GrantStarters`, `PullSingle`, `PullTen`, `Save`, `Reload` API를 제공합니다. 외부에 제공하는 `Snapshot`은 깊은 복사본이며 UI는 이 복사본에서 천장 항목을 조회합니다. 실패한 교환이나 모집은 부분 차감하지 않으며 결과 이벤트는 저장 성공 후 발행합니다. 연출 스킵은 `PresentationRequested`만 억제하고 `PullCommitted`와 결과는 유지합니다.

`M15GachaDemo`의 `Catalog`, `Manager`, `SelectedBanner`, `LastResults`(`IReadOnlyList<PullResult>`), `PresentationRequestCount`로 통합 상태를 조회할 수 있습니다. `SelectBanner(int)`, `PullSingle()`, `PullTen()`, `ExchangeTickets(int)`, `GrantStarters()`, `Save()`, `Reload()`는 UI 버튼과 동일한 경로를 호출합니다. 테스트는 `M4Session.UseProgressForTests`로 임시 저장 서비스를 먼저 주입하여 실제 사용자 저장에 접근하지 않습니다.

## 주요 데이터 구조

| 타입 | 저장/설정 내용 |
| --- | --- |
| CharacterDefinition SO ×18 | Id, DisplayName, Element, Rarity, Role, Weapon, IsStarter |
| GachaRules SO ×1 | 3/4/5성 확률, 소프트·하드·4성 천장, 픽업 확률, 교환 비용 |
| GachaBanner SO ×2 | 안정 ID, 이름, 종류, 픽업, 3/4/5성 후보 배열, 공통 Rules 참조 |
| GachaCatalog SO ×1 | 18명 캐릭터와 2개 배너, 공통 Rules 참조 |
| EconomySaveData | 6개 정수 잔액, 동료 ID별 copies, 배너 ID별 5성/4성 미당첨 카운터·픽업 보장, 스타터 무료 지급 여부, revision |

재화 enum 순서는 JSON의 balances 인덱스 계약이므로 기존 값을 재정렬하지 않습니다. 저장된 미등록 동료/배너 ID도 보존하여 카탈로그 변경 시 소유 정보가 사라지지 않게 합니다. 중복 동료는 장수만 누적하며 승급이나 별도 재화 변환은 이 단계에 추가하지 않았습니다.

호출 예시:

~~~csharp
var wallet = CurrencyManager.Instance;
wallet.Add(CurrencyType.OrbitShard, 160);
wallet.Exchange(CurrencyType.LimitedPledge);
wallet.PullSingle(wallet.Catalog.Banners[0], out PullResult result);
wallet.PresentationRequested += rarity => Debug.Log((int)rarity + "성 연출 연결");
// 전투 모델·파티 편성은 바꾸지 않으며, UI 연출 연결은 성공한 저장 뒤 실행된다.
~~~
## 자동 검증

Unity Test Runner의 EditMode에서 `Orbis.M15.Tests` 테스트들을 실행합니다.

- `GachaEngineTests`: 확률 경계, 74/90번째 천장, 10회 보장, 50/50 실패 후 보장, 배너 독립성, 균등 선택, 잘못된 RNG와 데이터 거부를 검증합니다.
- `EconomyPersistenceTests`: 저장 버전 이전, 6종 재화와 교환, 원자적 10회 모집, 저장 실패 롤백, 보장 유지, 무료 스타터의 1회 지급, 기존 M4 보상과 루멘 공유를 검증합니다.

PlayMode의 `GachaDemoTests`는 실제 `M15_GachaDemo.unity`를 열어 모집 결과·스킵·저장 유지·배너 전환과 데이터 구성을 검증합니다. 테스트 케이스의 통과 여부는 실행 결과 XML로 확인하며, 난수의 큰 표본에서 빈도를 추정하는 방식 대신 제어한 난수로 경계와 저장 동작을 확인합니다.

Unity 6000.6.0f1에서 최종 EditMode 255개와 PlayMode 46개, 총 301개가 모두 통과했습니다(실패·스킵 0). 기존 시스템 회귀 테스트를 포함합니다. 새 검증은 Core 51개, Persistence 20개, 데모 PlayMode 2개, 파일 잠금 보호 1개입니다.

- TestResults/M15-setup.log: 18개 캐릭터·2개 배너·공통 규칙·카탈로그·씬 생성/참조 검증
- TestResults/M15-EditMode.xml 및 .log: 255개 통과
- TestResults/M15-PlayMode.xml 및 .log: 46개 통과

v2에서 재화 section·배열이 빠진 손상 파일은 유효한 빈 계정으로 초기화하지 않습니다. 본문 파일이 일시적으로 잠긴 경우에도 과거 백업을 쓰기 가능한 상태로 열지 않고, 정상 재로드 전까지 저장을 차단합니다. 파일 잠금·부분 쓰기·이벤트 순서·마이그레이션을 포함한 모든 자동 테스트는 GUID 임시 저장을 사용했습니다.
